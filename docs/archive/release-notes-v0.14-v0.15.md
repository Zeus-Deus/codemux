# Codemux Release Notes Archive (`v0.14.0` – `v0.15.6`)

- Purpose: Historical per-release implementation notes moved out of `docs/core/STATUS.md`.
- Audience: Anyone tracing when and why a subsystem got its current shape.
- Authority: Historical record only. For current truth read `docs/core/STATUS.md`; for build order read `docs/core/PLAN.md`; for current subsystem behavior read `docs/features/*`.
- Update when: Never — append-only. New releases are summarized in `docs/core/PLAN.md` and, while recent, in `docs/core/STATUS.md`.
- Read next: `docs/core/STATUS.md`, `docs/core/PLAN.md`, `docs/archive/release-notes-v0.6-v0.13.md`

These paragraphs lived in `STATUS.md`'s "Current Headline" section. They are the direct
continuation of `docs/archive/release-notes-v0.6-v0.13.md` and were moved for the same

## Notes

Shipped in `v0.15.6` (2026-07-30) — six merged PRs, in four clusters:

- **Chat code rendering** (PR #216). Fenced code blocks in Agent Chat are syntax-highlighted with Shiki instead of rendering flat grey, and the token colors come from the **live terminal ANSI palette** — so a keyword is the same color in chat, the file editor, and a terminal pane, and switching terminal theme recolors chat live. New `src/lib/shiki-chat-theme.ts` (`buildChatCodeThemes` → a light/dark pair on a transparent background) + `src/hooks/use-chat-code-plugin.ts`, a **module-level store** rather than a per-component hook so a transcript's N `ChatMarkdown` instances share one `get_current_theme` IPC call and one `theme-changed` listener. Streamdown owns the code card, so `ChatMarkdown`'s `prose-*` chain only neutralizes the typography defaults while `globals.css` styles the card; line numbers are off (with an explicit line-box restore, since Streamdown's `display:block` rides on the line-number class) and a language-less fence hides its header strip. New Settings → Appearance → **"Wrap code in chat"** (`chat.code_wrap`, default off; since PR #236 it supplies each card's `data-wrap` default rather than a root-level attribute). A follow-up fixed a stale-color bug: `@streamdown/code` caches highlighters by theme **name**, and the name hash covered a hand-picked field list, so two palettes differing only in `color9` (reachable solely through the `invalid` scope) collided on one name — `themeId` now hashes the **built** theme, putting every color the token map consumes into the identity by construction. See `docs/features/agent-chat.md` § "Code blocks in chat" and `docs/reference/DESIGN-SYSTEM.md`.
- **Provider-request lifecycle** (PR #220). Answering an approval or `AskUserQuestion` that outlived its provider session no longer errors confusingly or spawns a useless replacement session. Claude/Codex keep those callbacks only in the live sidecar/app-server process, so `agent_chat_respond_to_request` now checks `has_session()` first and, for providers that don't survive a restart, persists `RequestResponseFailed { reason: "stale_provider_callback" }` — the control terminalizes with "This request expired when the provider session restarted. Continue to have the agent repeat it.", the linked tool card goes to `error`, a linked workflow goes to `stopped`, and the pane maps to `Review`. All three adapters converge on one new `ProviderError::RequestNotPending`: Codex returns it directly, OpenCode maps HTTP 404/409/410 onto it, and Claude derives it from the sidecar's `InvalidParamsError` rethrow. Two follow-ups keep it honest — **OpenCode opts out** (its permission state lives in the external HTTP server, so `pending_requests_survive_session_restart` is `true` and hydration mirrors that through the pure frontend table `providerRequestsSurviveSessionRestart`, leaving its requests answerable after a pane remount), and the reducer **refuses to expire an already-`resolved` request**, because providers can't distinguish "unknown request" from "already answered" and this event is persisted, so a duplicate respond would otherwise flip an answered approval to "expired" on every replay. See `docs/features/agent-chat.md` § "Pending requests are not conversation history".
- **Skills + command discovery** (PRs #217/#218). Project-scope Codex skills under `<project>/.agents/skills/` are discovered (previously only the Codex CLI saw them), and `enumerate_scan_paths` became the single source of truth for scan roots with **canonical-path dedup**, so aliased roots stop double-listing. The `skills_sync` path table was brought back into lockstep with it — `~/.agents/skills/` and `~/.config/opencode/skills/` were being discovered but silently dropped from sync with no diagnostic — and two guard tests now drive the real enumeration through the classifier and fail the build on drift. Separately, the `/` popup stops offering commands the user can't use: internal Claude CLI commands are filtered by a `__` prefix rule plus an exact denylist (54 discovered → 48 shown), and same-named skills reachable through multiple roots collapse to one row whose body is guaranteed to be the one injected at send time (`dedupeSkillsByName` + first-wins `parseSkillTokens`). The filter is **menu-only** — a hand-typed command is still forwarded verbatim. See `docs/features/skills-sync.md` and `docs/features/agent-chat.md`.
- **Sidebar inbox detail** (PRs #219/#221/#234). Settled rows regained a state-colored, directly clickable PR badge (icon + `#number`, disabled and dimmed with no `pr_url`), and the workspace inbox now follows **PR-completion settlement**: merged or closed PR work settles immediately whenever it is not working or blocked, including completed-review and currently-open workspaces (the old one-hour merged-PR grace, `MERGED_PR_SETTLE_IDLE_MS`, is gone). The PR refresh that feeds this settlement now resolves all states by explicit branch/repository identity instead of implicit `gh pr view` plus exact local/remote SHA equality, so review commits can no longer make a merged badge disappear before settlement (PR #234); open PRs win on reused branches, default-branch history is suppressed, fork-tracking branches query the bare branch name and are disambiguated by head-repository owner client-side (`gh --head` does not match the `owner:branch` form), and an unanswerable lookup — failed, timed out, or a detached HEAD mid-rebase — retains the last known badge. Settlement never navigates away; the highlighted row is force-rendered in the Settled shelf, and a manual Un-settle pins it active until a genuinely *new* status edge. Command search indexes title, branch, and project path across active and settled records via `workspaceCommandValue`. Row activation is scoped to the row node (`isRowActivationKey`), so Enter/Space on the PR badge, Un-settle, or Wake now runs only that control. On active cards the meta line became two columns so PR chips share one right edge down the list. See `docs/features/sidebar.md`.

Shipped in `v0.15.5` (PR #211) — **an Agent Chat pane can no longer pick its scope, because its workspace already fixed it.** A workspace owns exactly one project root and one checkout (`cwd` / `worktree_path`), shared by every tab, surface and pane inside it — but `AgentChatPane`'s empty-thread `ThreadScopeRow` offered both a "New worktree" checkout control and a project location picker, on EVERY additional chat tab (including tabs of a workspace that was already worktree-backed). Neither rescoped the thread: "New worktree" created a SECOND workspace off the parent repo mid-send and relocated the user into it, orphaning the tab (and its already-started session) behind an app-wide workspace flip; the location picker activated another project's first workspace (or opened the new-workspace dialog), abandoning whatever had been typed. Both were app-wide relocations wearing per-thread clothing. `ThreadScopeRow` is now `DraftChatSurface`-only — the one surface where the question "what should the first send create?" has an answer, because nothing exists yet — and the pane renders the read-only Context Row from its first render, so the strip never changes shape across the first send. Creating a worktree belongs to the draft surface and the sidebar worktree flow; switching project/workspace belongs to the sidebar. Deleted: `handleDeferredWorktreeSubmit`, `src/lib/agent-chat/prestart-worktree-session.ts` (+ test), the row's `ThreadScopeLocation` / `ThreadScope` discriminated props (flat props again, one consumer), its `trailing` slot, and `LocationControl`'s workspace-mode branches. Backing that up in Rust: `create_worktree_workspace_impl` gained an **adopt-existing guard**. `git_create_worktree` can return an ALREADY-EXISTING checkout without creating anything (its path-reuse short-circuit, when the conventional path is on disk and registered to the same branch), and the impl used to call `create_workspace_with_layout` regardless — minting two workspaces over one on-disk worktree, i.e. two agents editing the same files. It now looks for a live local workspace already claiming that path (`worktree_path`, falling back to `cwd`; canonicalized comparison; remote/attach-only rows excluded) and adopts + focuses it instead, skipping PTY spawn, setup scripts, `.mcp.json` rewrite, and preset launch; `initial_prompt`/`agent_preset_id` are deliberately dropped rather than injected into someone else's live session, and archived workspaces neither block nor get silently un-archived. Verified with `npm run check`, `npm run test` (3026), `cargo check`/`cargo test` (2261), and a dev-mock browser drive of both surfaces. See `docs/features/agent-chat.md` § "Thread Scope (first-send scope controls)".

Shipped in `v0.14.2` (PR #184): **null-mode launch heal — the actual root cause of "Full access still prompts."** The PR #178 sidecar guard above turned out to be aimed at the wrong layer: the recurring reports (Allow/Deny cards while the composer pill shows "Full access", main-workspace panes only) came from the session-history dropdown's New Chat and resume flows (`src/hooks/use-agent-chat-session-actions.ts`), the ONE launch path that passed `permission_mode: null` to `agent_chat_start_session`. The SDK then booted the CLI in `default` mode while the fresh store slice's pill defaulted to `bypassPermissions` and the DB row stayed NULL (`keep_or_set(None)`), and the sidecar guard never fired because the sidecar's intended mode read `undefined`, not `bypassPermissions`. Worktree/draft/fresh-pane launches all passed a real mode — hence "only main threads." Two-layer fix: the hook now passes `DEFAULT_THREAD_PERMISSION_MODE` on New Chat and the record's persisted config (mode NULL-healed to the provider default, plus model/effort/context window) on resume, then seeds the slice's `permissionMode` AND `sessionLaunchMode` so pill, restart detection, and launch agree; and `agent_chat_start_session` (`src-tauri/src/commands/agent_chat.rs`) heals a `None` `permission_mode` to `fallback_permission_mode(provider)` before the provider consumes the input and persists the healed value — same rationale as the `ensure_live_session` heal — so no future null-passing caller can launch a session in a mode the UI doesn't display. Verified with `npm run check`, `npm run test` (new hook tests), and `cargo test`. See `docs/features/agent-chat.md` § "Session lifecycle" ("Null-mode launch heal").

Shipped in `v0.14.1`: **Full-access silent-downgrade heal for Claude Agent Chat** (PR #178). (Superseded by the PR #184 null-mode launch heal below, which fixed the actual root cause.) Shipped in `v0.14.1`: **stale-Claude-session self-heal** (PR #177). A thread's persisted `sdk_session_id` goes stale when the CLI's on-disk conversation JSONL disappears (cleanup, version updates); resuming it made every turn fail with `error_during_execution — No conversation found with session ID` and nothing cleared the dead cursor, so the thread stayed wedged across restarts until the user made a new one. Three recovery layers now fire (`sidecar/claude-agent/src/session.ts`, `src-tauri/src/agent_provider/claude/protocol.rs`): the sidecar detects the stale-resume result (or thrown error, since the CLI validates `--resume` eagerly before any turn exists), suppresses it, emits a resume-fallback notification, rebuilds a fresh query with all resume state cleared, and replays the pending user turn so the send transparently succeeds (one recovery per turn). Verified end-to-end against the real CLI plus new sidecar `session.test.ts` cases. See `docs/features/agent-chat.md`.

Shipped in `v0.14.0` (default-off): **web remote access** (PR #163) plus its **account/relay/hosted follow-on stack** (account-mode Stage A #166, browser-WASM iroh transport + `app.codemux.org` hosted bootstrap #167, GitHub OAuth sign-in for the hosted web client #168, `codemux remote pair` CLI + Tailscale-only bind scope) — the desktop app grows an embedded, **default-off** HTTP + WebSocket server (new `src-tauri/src/web_remote/`, axum, in the desktop process) so a browser on another device (laptop, phone on the LAN or the user's mesh VPN) loads the *same* UI bundle and drives the *same* running instance — same projects, workspaces, terminals, agent chats. It is a **UI transport** (a second frontend for one backend), the sibling of the remote-hosts **compute transport** (same frontend, remote backend), and the two compose: a paired web client transparently sees and drives the desktop's remote hosts with no web-specific host code. The seam is `window.__TAURI_INTERNALS__` — the production twin of the dev-mock shim (`src/remote/shim.ts`) backed by a real WebSocket instead of fixtures, so **zero app components change**; `main.tsx` selects real-IPC / dev-mock / web-shim three ways and both shims stay dormant under the desktop WebView. Invokes dispatch through the main webview's own `on_message` (reusing arg deserialization + `State`/`AppHandle` extraction + ACL + error formatting for all ~300 commands with no per-command wiring); a `Builder`-registered channel **interceptor** + `ChannelRouter` re-route each command's `Channel` frames to the owning browser (JSON `chan` frames, or the compact `[0x01][u32 cb][u64 idx][payload]` binary frame for PTY bytes), and a `listen_any` **event hub** multiplexes all subscribers onto one desktop listener per event name. Auth is **pairing-token → persistent revocable session**: a 32-byte, 10-min, single-use pairing token (QR / `#pair=` deep link) is traded at `POST /api/pair` for a SQLite session (SHA-256 at rest, constant-time compare, no early-return), and the session is traded for a 30s single-use **WS ticket** so the session secret never lands in a `/ws` URL; credentials ride a `Bearer` header or an `HttpOnly; SameSite=Strict` cookie through one `authenticate`; optional **approval mode** holds a new pairing pending until the desktop approves; **revocation severs live sockets** immediately (frame `Close` + trip a `watch`). Origin checks guard every state-touching route, pairing is rate-limited 5/min/IP keyed on the real TCP peer, and the browser-pane proxy validates the loopback port range + rejects control chars. Multi-client is **mirror mode** (all clients share `AppStateSnapshot` incl. focus); the terminal + agent-chat streams now **fan out** to N subscribers (per-generation attach/detach, replay only to the new attacher, pause only when ALL subscribers pause), and the **desktop window owns scrollback serialization** (web clients no-op it). Web fallbacks are gated on `isRemoteClient()` so desktop stays byte-identical: an in-app **path browser** replaces the native file dialog (unlocking **opening projects / creating workspaces from the browser**), **Web Notifications** (toast fallback) mirror desktop notifications, `convertFileSrc` → an auth-gated `/api/assets` streamer, the loopback `agent-browser` daemons are reached through an authed WS/HTTP **browser-pane proxy**, window chrome is hidden, and the desktop stays the single updater — it publishes availability to paired browsers, defers its auto-update restart while remote devices are attached, and a browser can trigger the desktop's download-and-restart. `web_remote_list_endpoints` enumerates loopback / LAN / tailnet / MagicDNS with per-endpoint **secure-context** notes (only loopback is secure over plain HTTP; TLS is delegated to the mesh VPN's HTTPS serve or a user proxy in v1). On top of that v1 LAN/pairing base, the follow-on stack adds three things, all **default-off** and additive under the same `/ws` frame contract (transport swaps only): (1) **account-mode admission** (`POST /api/pair-account`) — a browser on a reachable LAN/tailnet endpoint signs into the *same* Codemux account the desktop is signed into instead of scanning a QR (raw password never leaves the browser; the desktop verifies same-`user.id` via `/api/auth/desktop/signin` + `load_cached_user`; account sessions default to pending-approval); (2) **`codemux remote pair`** — mint a pairing code + terminal QR over the same-machine control socket while SSH'd in, no GUI needed; and (3) the **from-anywhere hosted/relay tier** — the desktop becomes an **iroh** endpoint (`src-tauri/src/web_remote/{iroh,registration}.rs`, `iroh = "1"`, gated by a **relay-mode** toggle), self-registers its `NodeId` with the `api.codemux.org` device registry, and a browser at the hosted static client `app.codemux.org` (built via `npm run build:iroh-wasm` + `VITE_CODEMUX_HOSTED=true`; GitHub OAuth or email/password sign-in) picks a device and drives it over an **E2E-encrypted QUIC** stream (hole-punched, or ciphertext through public relays — decision-9 clean). The hosted service is **not yet live**: the `app.codemux.org` static host and the `api.codemux.org` device-registry endpoints are gated human deploys (runbook: `docs/plans/app-codemux-org-hosting.md`), so real cross-network iroh connectivity is exercised only against mocks + unit/integration tests until then. The localStorage session is a documented shared-machine trade-off (revoke severs instantly). Debug-only e2e affordances (`web_remote::e2e_autostart`, `auth::seed_dev_offline_login`, dev `?remote=1`) are all `#[cfg(debug_assertions)]` **and** env-gated, so no release path is weakened.
