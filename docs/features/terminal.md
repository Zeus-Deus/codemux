# Terminal System

- Purpose: Describe the PTY-based terminal subsystem powering all terminal panes.
- Audience: Anyone working on terminal rendering, shell integration, or PTY management.
- Authority: Canonical feature doc for the terminal layer.
- Update when: PTY behavior, rendering, shell integration, or session lifecycle change.
- Read next: `docs/features/presets.md`, `docs/reference/SHORTCUTS.md`

## What This Feature Is

The terminal system provides multi-session PTY terminals rendered with xterm.js. Every terminal tab is a real pseudoterminal spawned by the Rust backend, with data streamed to the React frontend via Tauri channels.

## Current Model

The Rust layer uses `portable-pty` to spawn shells. Each terminal session has a master PTY handle, a read thread, and a write path. The frontend renders with xterm.js's **WebGL renderer** (`@xterm/addon-webgl`) **only where it is verifiably a win**: it offloads glyph rasterization to the GPU, the recommended renderer for the fast, long-running agent output Codemux streams — but loading it on the wrong GL stack ships per-keystroke input lag (the `v0.9.0` typing-lag regression; the same lesson was first learned in `acd1566`, v0.1.33). A one-time probe (`webgl-renderer-probe.ts`) decides before the addon loads:
  - **Software WebGL** (SwiftShader, llvmpipe, swrast, Microsoft Basic Render Driver — VMs without GPU passthrough, blocklisted drivers) → **DOM renderer**. Detected via the unmasked `WEBGL_debug_renderer_info` string on engines that report it honestly (Chromium family: Windows WebView2, the dev-mock browser).
  - **Linux WebKitGTK (the Tauri app webview on Linux)** → **DOM renderer, by policy**. Modern WebKitGTK *masks* the renderer string for fingerprinting resistance (it literally reports "Apple GPU" on Linux), so hardware backing is unverifiable from inside the page — and this engine has a twice-documented WebGL input-lag history. A `localStorage["codemux:terminal-renderer"] = "webgl" | "dom"` override allows live A/B testing.
  - **Everything else** (Windows WebView2 with real GPU strings, macOS WKWebView where "Apple GPU" is true and Metal-backed) → **WebGL renderer**.

When the probe passes, the addon is loaded after `term.open()` (it needs the opened terminal's DOM element) and registers an `onContextLoss` handler that disposes it so xterm falls back to its DOM renderer if the GPU drops the canvas context; construction is wrapped in try/catch so an environment without WebGL2 support also falls back to the DOM renderer instead of breaking the pane. Data flows: PTY read thread -> Tauri channel -> xterm.js write. User input flows: xterm.js onData -> Tauri command `write_to_pty` -> PTY master write. PTY output delivery clones the Tauri channel under the session lock and sends outside that lock, so active keystrokes do not block behind IPC delivery for busy terminals.

### Terminal Pane Lifecycle (per-mount) + throttled write pump

The live terminal render path is `src/components/terminal/TerminalPane.tsx`. Each pane constructs its own xterm.js `Terminal` (WebGL renderer, DOM fallback) on mount and disposes it — including the WebGL addon — on unmount. Because `src/components/layout/workspace-main.tsx` only renders the active workspace and `PaneContainer` only renders the active surface (tab), switching workspaces or tabs **unmounts** the previous pane tree and **mounts** the new one — terminals are rebuilt from scratch on every switch (a fresh xterm + scrollback restore + PTY reattach).

To keep that switch from freezing the UI, every byte destined for xterm — disk-scrollback restore, the PTY reattach replay, and steady live output — is funneled through a single throttled write pump (`src/components/terminal/terminal-write-pump.ts`). The pump drains a bounded byte budget per macrotask and yields between batches, so a multi-MB `attach_pty_output` replay (the backend replays the whole `pending_output` ring on every attach) fills in over a few frames instead of blocking the click + visibly "pouring in". Historical bytes are enqueued **before** the live channel attaches, so the single FIFO drain preserves xterm's stateful parse order (alt-screen / cursor state across the history→live boundary).

On unmount the outgoing pane persists its buffer for restore — **except** for alternate-screen buffers (the long-running TUI agents: Claude Code, lazygit, vim, btop), whose serialized content is garbled and is never restored anyway. Serializing those is skipped (`buildScrollbackPayload` returns empty `data` when `alternate_buffer`), which removes the dominant synchronous cost from switching away from an agent pane. The screen is reconstructed on return by the PTY reattach replay (`attach_pty_output` replays the full `pending_output` byte history, which re-enters alt-screen and redraws — this is why the backend retains the full ring rather than only post-detach bytes; trimming it would blank an idle agent on return).

For ordinary shells the exposure is the reverse: a deep scrollback makes `serializeAddon.serialize()` the dominant cost of the switch — the known >30ms hotspot (issue #128). That serialize is now moved **off** the latency-critical unmount path by a per-pane idle serializer (`scrollback-idle-serializer.ts`). While output is quiet it opportunistically serializes the buffer in a `requestIdleCallback` slot and caches the result, so on unmount (and on the app-close serialize dance) `buildScrollbackPayload` reuses that cache when it is still clean and skips the serialize entirely — the switch pays nothing. If the cache is stale (output arrived, or a resize reflowed the buffer) it falls back to today's synchronous serialize, so persistence never regresses. The idle serializer is fed off the write pump (its `notifyOutput` runs per chunk, kept O(1) so the per-keystroke echo path stays cheap) and disposed before `term.dispose()` so a pending idle callback can't serialize into a torn-down terminal. See `docs/features/session-persistence.md` for the full serialization model.

Even a cheap teardown is still work the incoming pane has to wait behind, so the unmount cleanup no longer runs inline: it **parks** a job that executes after the new selection has painted (`src/components/terminal/deferred-teardown.ts`). `TerminalPane`'s cleanup calls `parkTeardown({ sessionId, run })`, and the scheduler waits a double `requestAnimationFrame` and then a `requestIdleCallback` (500 ms timeout; `setTimeout` fallbacks at 0 ms / 200 ms for engines advertising neither, which includes older WebKitGTK and jsdom) before the serialize + `term.dispose()` happen. Three bounds keep deferral from becoming a leak:

- **At most two parked jobs** (`MAX_PARKED_TEARDOWNS = 2`). Parking a third drains the oldest **synchronously** first, so the queue can never grow with a fast switcher, and each job runs exactly once (`ran` flag, `run()` wrapped in try/catch logging `[codemux::terminal-teardown]` so a failed teardown cannot take down a mounting pane).
- **Same-session flush before remount.** `parkTeardown` flushes any pending job for the same `sessionId` first, and the mount effect calls `flushTeardown(sid)` at its very top — before `new Terminal(...)` — so a stale serialize can never land after a newer one or write into a torn-down terminal.
- **WebGL contexts stay bounded.** The parked job still disposes the WebGL addon, so at most `MAX_PARKED_TEARDOWNS` extra GL contexts exist and only transiently — the failure mode that sank the earlier persistent-cache experiment against the browser's ~16-context ceiling (`14735bf` → `2baa42f`, cited in the module header). A pane parks its job whether or not `session_restore.enabled` is on, so that bound is identical in both states; only the serialize half is skipped when restore is off. When restore is on, the serialize is wrapped in the interaction-trace `terminal-teardown` sub-measure (see `docs/features/observability.md`).

> **Historical note — persistent xterm cache (disabled).** A module-level cache (`src/components/terminal/terminal-cache.ts`) that kept xterm instances alive across switches and reparented a wrapper `<div>` into a `#codemux-terminal-parking` node was shipped in `14735bf` and **rolled back** in `2baa42f` for input-lag / malformed-render regressions. The file is retained but **not wired into the live app** (see its top-of-file banner) as the basis for a possible future flag-gated revival — the "keep instances alive" approach is the true-instant fix but must be live-verified first. Its flow-control / backpressure and throttled-replay code is therefore **inert in production**; `terminal-write-pump.ts` is the live equivalent of the throttle, and the live `TerminalPane` is now the path that actually engages PTY producer back-pressure (the cache's HIGH/LOW watermark *constants and approach* were reused there — see "PTY producer back-pressure" above). `useTerminalCacheGc` and `useTerminalThemeSync` (wired in `App.tsx`) operate on the empty cache map and are likewise no-ops today.

## What Works Today

- multiple concurrent terminal sessions per workspace
- shell detection:
  - **Unix**: respects `$SHELL` and falls back to `/bin/bash`
  - **Windows**: prefers `pwsh.exe` (PowerShell 7+) when on `PATH`, falls back to `powershell.exe` (Windows PowerShell 5.1, pre-installed on every supported Windows version), then `%COMSPEC%`, then literal `"cmd.exe"`. PowerShell wins because the Windows preset wrappers emit PowerShell `$env:VAR` syntax for context injection — see `agent_context.rs` and `docs/features/presets.md`
- PTY resize on pane/window resize
- xterm.js WebGL renderer (GPU glyph rendering) gated by a once-per-session probe: DOM renderer on **software-rendered WebGL** (SwiftShader/llvmpipe-class stacks) and on **Linux WebKitGTK** (masked renderer strings + input-lag history; `localStorage["codemux:terminal-renderer"]` overrides), with the existing fallbacks on GPU context loss or missing WebGL2 support, plus kitty keyboard protocol support
- terminal theme reads dynamically from CSS variables via MutationObserver
- session state tracking — `TerminalLifecycleState { Starting, Migrating, Ready, Exited, Failed }` and the persisted `TerminalSessionState { Starting, Ready, Exited, Failed }`
- environment injection: `CODEMUX`, `CODEMUX_VERSION`, `CODEMUX_WORKSPACE_ID`, `CODEMUX_BROWSER_CMD`, `BROWSER`, `CODEMUX_AGENT_CONTEXT`
  - `strip_renderer_env` removes the three WebKit renderer variables (`WEBKIT_DMABUF_RENDERER_FORCE_SHM`, `WEBKIT_DISABLE_DMABUF_RENDERER`, `WEBKIT_DISABLE_COMPOSITING_MODE`) from every child shell — both spawn paths and the pty daemon — so a GTK/WebKit app launched from a Codemux terminal picks its own renderer instead of inheriting the app's choice. See `docs/features/agent-chat.md` § "Perf on Linux WebKitGTK".
- working directory set to workspace root on creation
- **live cwd hint in the pane header**: the terminal pane header used to render a bare `"Terminal"` — the same word the tab directly above it already shows, so the strip carried no information. It now appends the session's live working directory *only when it differs from the workspace root*, e.g. `Terminal · src-tauri`. At the root (the common case, and where every session starts) the header is unchanged, so it reads as "signal only when you've wandered somewhere unexpected" rather than churning on every pane. Deep paths elide their head (`…/src/pty_daemon`) and out-of-workspace paths contract against `$HOME` (`~/dotfiles`); the untrimmed path is on the hover tooltip. Long absolute paths are deliberately not rendered in full — the header is a 28px strip that CSS-truncates on the *right*, so one would degrade to `/home/zeus/.codemux/worktr…` and drop the only segment that mattered. A short outside path (two segments or fewer) *is* shown in full, **keeping its leading slash** (`/var/log`, not `var/log`) so it can never be misread as a workspace-relative path.
  - **Two sources, `osc7` beats `proc`.** `TerminalPane` registers an xterm OSC 7 handler (`ESC ] 7 ; file://host/path ST`, which shells with integration push on every prompt) — event-driven, exact, and the only source that works for remote/SSH panes where the shell's pid is on another machine. Shells without that integration (a bare zsh is common) fall back to `terminal_session_cwds`, a Rust command that readlinks `/proc/<pid>/cwd` for the session's **shell** pid — so `cd` moves the header but a long-running child (a build, an agent) does not. Once a session reports via OSC 7 the poller drops it from its request set entirely, so a fully shell-integrated setup costs zero IPC. OSC 7 payloads are normalized for Windows drive paths (`file:///C:/Users/...` → `C:/Users/...`) so root matching works there. The `/proc` fallback is **Linux-only** (`read_process_cwd` compiles to `None` elsewhere), so on Windows and macOS OSC 7 is the only source — a shell without the integration simply shows no hint.
  - **State lives in the frontend, not the snapshot.** `TerminalSessionSnapshot.cwd` remains the *spawn* directory (written once at creation, never refreshed) — making it live would fan out a full state rebuild plus a persistence write on every `cd` for a cosmetic label. The live value sits in `terminal-cwd-store.ts` and is rederived within one poll interval of launch. Pane titles stay write-once, and the cwd is appended as a separate element rather than replacing `node.title`, because `PRESET_TITLE_TO_ICON` in `PaneNode.tsx` keys the preset icon off the exact title string.
- comm log support for OpenFlow agent communication tracking
- ANSI code stripping for log capture
- **lifecycle status overlay** (`TerminalPane.tsx`, `updateStatusOverlay`): a centered card driven imperatively from the `terminal-status` event via direct DOM mutation (no React re-render — status fires per IPC tick). Covers `starting` (spinner + "Terminal starting"), `failed` (warning dot + "Terminal unavailable" + exit code), and a distinct **`migrating`** state ("Migrating workspace" + the host-specific message) shown during a cloud-push / pull-back transition — see `docs/features/remote-hosts.md` § *Migration overlay*. On `ready` (or the first output byte on a migrating pane) the overlay fades out via a CSS opacity transition (`.terminal-overlay` in `globals.css`, kept in sync with `OVERLAY_FADE_MS`) before `display:none`, so it doesn't snap away the instant a (re)spawned session comes alive. `migrating` rides the `terminal-status` event only; it collapses to `Starting` in the persisted session state (`TerminalLifecycleState` → `TerminalSessionState` in `terminal/mod.rs`), so overview/sidebar/persistence consumers are untouched.
- **throttled write pump (live path)**: every byte destined for xterm goes through `terminal-write-pump.ts`, which drains a bounded byte budget per macrotask and yields between batches. This keeps a fast producer (`yes`, `cat huge-file`, a verbose build, a runaway agent) and — more importantly — the multi-MB `attach_pty_output` reattach replay on every workspace switch from pegging the renderer's main thread. It is the consumer-side throttle that prevents the switch freeze.
- **idle scrollback pre-serialization (live path)**: a per-pane idle serializer (`scrollback-idle-serializer.ts`) serializes an ordinary shell's buffer while it is quiet (settled ≥1s, ≥5s between serializes) in a `requestIdleCallback` slot and caches it. The unmount/close path reuses that clean cache and skips the synchronous serialize — the workspace/tab switch pays nothing — falling back to a fresh serialize when the cache is dirty (issue #128). Alt-screen panes are never idle-serialized; resizes invalidate the cache.
- **PTY producer back-pressure (live path — engaged in production)**: the throttled write pump alone only slows the *consumer*; a fast producer (`yes`, a verbose build, a runaway agent) can still outrun xterm's ~5–35 MB/s ingest and balloon the renderer queue (and, while detached, overflow the 256 MiB `pending_output` ring into dropped scrollback). The live `TerminalPane` now watches the pump's queued-byte depth and signals the producer: when queued bytes cross a HIGH watermark (16 MiB) it calls `pause_pty_output`; when they drain below LOW (4 MiB) it calls `resume_pty_output` (hysteresis avoids thrashing — watermark logic + callbacks live in `terminal-write-pump.ts`, wired in `TerminalPane.tsx`). Pausing stops the read loop draining the PTY master fd, so the child blocks on `write()` once the kernel buffer fills — real back-pressure to the producer.
  - **Both spawn paths honor it.** Daemon-backed sessions route the pause/resume to the daemon's `SetFlowPaused` (v2 wire protocol) and its read loop's `flow_paused` gate. In-process (non-daemon) sessions now honor a per-session `flow_paused: Arc<AtomicBool>` that `batched_reader_loop` polls — **previously a deliberate no-op, fixed for issue #73** so the fallback path (Windows, daemon-disabled, daemon failure) gets real back-pressure too.
  - **Self-heal (both paths).** A paused PTY always resumes even if the matching resume is lost: the in-process reader clears the flag on `attach_pty_output` (a reattaching pane starts live) and `detach_pty_output` (a backgrounded agent isn't left blocked), plus a 10 s `FLOW_MAX_PARK` backstop inside the read loop; the renderer also resumes explicitly on unmount. The daemon mirrors this (clears on `Attach`/`Close` + its own max-park). The throttled write pump remains the consumer-side complement — back-pressure does not replace it.
- session close kills the PTY child and its entire process group via a single `killpg(pid, SIGKILL)` through the central `terminate_pty_session` helper, so closing a pane/tab/workspace also tears down any Claude CLI, MCP server, or rust-analyzer the shell spawned. `portable-pty`'s Unix spawn path calls `setsid()`, so the shell is a process-group leader and `killpg` reaches its children. A previous version did SIGTERM → 200ms grace → SIGKILL; that grace window is exactly the adversarial case for PID recycling (the shell handles SIGTERM and exits in ~50ms, the kernel reuses the PID for an unrelated process, our SIGKILL lands on the wrong process group), so the current code goes straight to SIGKILL and collapses the race to microseconds. `impl Drop for SessionRuntime` is a safety net that kills the tree with a warning if the normal close path is ever skipped.

## Windows-Specific Notes

- **`portable-pty` is upstream `0.8.1`, not a fork.** Codemux briefly pinned `Zeus-Deus/portable-pty@codemux-0.8.1-no-window` to force `STARTF_USESHOWWINDOW + SW_HIDE`, but commit `06c0301` reverted to the crates.io release because `CREATE_NO_WINDOW` broke ConPTY pipe IO (blank panes). The console window is now suppressed instead by an `AllocConsole` + `SW_HIDE` on the *parent* process, gated `#[cfg(all(target_os = "windows", not(debug_assertions)))]`.

## Current Constraints

- no split-pane multiplexing within a single PTY (splits are separate sessions)
- no inline image rendering (sixel/iTerm2 protocols)
- scrollback persistence is plain text only (no image content from sixel/iTerm2)

Note: terminal scrollback is saved and restored across app restarts. See `docs/features/session-persistence.md` for the full persistence and adapter system.

## Important Touch Points

- `src/components/terminal/TerminalPane.tsx` — **the live terminal component**: per-mount xterm lifecycle, WebGL renderer load (gated on the hardware-GL probe; after `term.open()`, with `onContextLoss` → DOM fallback and a try/catch guard for no-WebGL2 environments; disposed on unmount), scrollback restore + reattach via the throttled write pump, ResizeObserver, focus, status overlay, custom key handler, alt-screen serialize skip, **idle-serializer wiring** (`buildFreshOrCached` fresh-if-clean reuse on unmount/close; `notifyOutput` fed from the pump's write callback; `notifyResize` from `term.onResize`; disposed before `term.dispose()`), **PTY back-pressure wiring** (pump HIGH/LOW watermark callbacks → `pause_pty_output`/`resume_pty_output`, resume-on-unmount)
- `src/components/terminal/scrollback-idle-serializer.ts` — **the idle serialize path (issue #128)**: per-pane opportunistic serializer that caches a clean serialization while the buffer is quiet so the unmount/close path can reuse it. O(1) `notifyOutput` per chunk (keystroke-echo safe — no per-chunk timer churn; re-arms one settle timer), `settleMs`/`minIntervalMs` cadence, `requestIdleCallback` with setTimeout fallback, alt-screen skip, resize invalidation, dirty tracking with fall-back-to-sync-serialize on unmount; injectable clock/scheduler; unit-tested in `scrollback-idle-serializer.test.ts`
- `src/components/terminal/webgl-renderer-probe.ts` — **the renderer gate**: one-time cached verdict on whether to load the WebGL addon. Declines on software rasterizers (SwiftShader, llvmpipe, softpipe, swrast, Basic Render Driver — honest Chromium-family strings) and on Linux WebKitGTK (masked "Apple GPU" strings make hardware backing unverifiable; engine has a documented WebGL input-lag history), honors the `localStorage["codemux:terminal-renderer"]` override, gives unknown strings elsewhere the benefit of the doubt, and logs the verdict once for diagnosability; unit-tested in `webgl-renderer-probe.test.ts`
- `src/components/terminal/terminal-write-pump.ts` — **the live freeze fix + back-pressure source**: ordered, byte-budgeted write queue that throttles scrollback restore + reattach replay + live output across macrotasks; also tracks total queued bytes and fires HIGH/LOW watermark callbacks (16 MiB / 4 MiB, with hysteresis) so the live path can signal the producer; unit-tested in `terminal-write-pump.test.ts`
- `src-tauri/src/terminal/mod.rs` — PTY spawning, read/write, session management, comm log locks, `attach_pty_output` (replays the full `pending_output` ring on attach — the reattach replay the write pump throttles; clears `flow_paused` as a self-heal), dropped-chunk observability counter, `pause_pty_output` / `resume_pty_output` flow-control commands, and the **in-process `flow_paused` gate** in `batched_reader_loop` (`set_pty_flow_paused` flips a per-session `Arc<AtomicBool>` the reader polls, with a `FLOW_MAX_PARK` backstop). In-process flow-control tests: `test_in_process_flow_control_pauses_and_resumes_reader`, `test_firehose_backpressure_bounds_backend_with_consumer_attached`
- `src-tauri/src/pty_daemon/{protocol,client,server}.rs` — `SetFlowPaused` wire request + per-session `flow_paused` flag gating the daemon read loop (with `Attach`/`Close`/max-park fail-safes); invoked by the live `TerminalPane` path for daemon-backed sessions (the in-process path uses `mod.rs`'s own `flow_paused` gate)
- `src-tauri/src/terminal/mod.rs` — `create_terminal_session`, `write_to_pty`, `resize_pty`, `attach_pty_output` (registered in `lib.rs` as `terminal::*`; `commands/workspace.rs` only reaches PTYs via `write_to_pty_by_session`)
