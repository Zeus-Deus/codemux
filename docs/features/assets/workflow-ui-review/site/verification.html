This page is secondary to the design review. It lists what the parent coding agent actually tested on the workflow runtime. The four UI mockups are illustrative and are not the native canary. No visual direction has been integrated into production.

● Native Claude coordination canary

  • The test ran on the real production WorkflowService, LiveWorkflowDriver, built Claude SDK sidecar and the installed Claude Code. It completed a native Claude Haiku 5.5 coordination test in 11.33 s.
  • The coordinator created two children and yielded its single worker slot. Each child read a separate fixture file and submitted 17 and 25. The coordinator then resumed and submitted sum 42 / child_count 2.
  • The run had four actual sessions and exactly three tasks, with no duplicate child runs.
  • In each session, the first-query SDK catalog contained exactly eleven captured host workflow tools and no native built-in tools.
  • All native sessions and owned process groups stopped with zero cleanup errors. Temporary source files were unchanged.

Spend accounting

  • SDK-reported costs across all functional attempts sum to $0.01005738.
  • Three sessions have incomplete final dollar counters. Each was assigned a conservative $0.20 allowance. Reported costs plus allowances total $0.61005738, against the authorized $2 functional-test cap.
  • This functional spend total excludes the separately requested Opus design generation that produced these mockups.
  • This is conservative accounting, not a complete invoice. The SDK's per-session budget can overshoot by a final API call. The session, turn, output and time limits left substantial margin.
  • Limits for the final successful run: 1024 output tokens per request, at most four sessions, six turns per session, an SDK budget of $0.20 per session, and a 90-second deadline.

Token-free suites

  • The affected workflow suite passed 72/72, and cargo check passed. These are real host tests with deterministic Claude/Codex-labelled provider fixtures, not live Codex inference.
  • They cover dynamic fan-out, capacity-one yield, typed failure repair, generation fencing, messaging, scoped artifact import, and source conflict-checked acceptance. They also cover preserving completed siblings across a SQLite reopen, and Unknown capacity held until verified reconciliation.
  • In the latest observed run, sidecar tests passed 47/47 and the typecheck passed. The native fake-RPC boundary passed 5/5. The frontend check and 25 affected workflow UI/mock tests passed.
  • Managed Rust filter checks passed 8/8.
  • The SDK is_error result-classification regression passed 1/1. The pure result classifier bug is fixed: an SDK result with subtype success and is_error: true is now classified as an Error, with its usage preserved.
  • The latest cargo check after these fixes passed.

Bugs repaired along the way

  • Completion arriving before ACK, and native event correlation.
  • A redundant first-turn model control that blocked startup.
  • Tracking when the model changes from A to B and back to A.
  • Artifact authorization for completed siblings in a later continuation.
  • Up-front loading of managed tools, and startup readiness.
  • SDK result classification: a result with subtype success but is_error: true was not treated as an error. It is now an Error, with usage preserved.
  • The 512-token native canary limit was too small and caused CLI API-error responses. 1024 succeeded. Not every earlier failure was caused by missing tools.

● Not established

  • Live support is limited to Claude and Codex on Linux in local Git workspaces, through scoped graph, file and result tools. The other four provider adapters remain dry-run only.
  • This small canary has not established native mixed Claude+Codex model coordination, large rewrites or runs with hundreds of workers.
  • The recovery evidence is a SQLite reopen within one test process, not a host-process crash test.
  • Native managed workers have no shell, build or test commands.
