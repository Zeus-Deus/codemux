# Plugin system: decisions the build spec left open

One line each: decision — why — how to revert.

- A Local plugin (a folder with no install marker) starts **on**; catalog and Git installs start off — you put a Local folder there yourself, and drop-in development needs it to run without a trip to Settings — make `defaultEnabledOf` in `src/contrib/runtime-loader.ts` return `false`.
- One recursive `notify` watcher on the plugins root, debounced 150 ms, emits `plugins_changed { id }` per changed folder (not per-file watches) — one watcher covers new folders, deletes and saves, and dot-folders (`.staging-*`) are ignored so installs don't flicker — replace `plugins/watch.rs` with per-entry watches.
- A registration's disposer removes that exact registration, not "whatever has this id now" — otherwise a hot reload's late cleanup could delete its own replacement — compare by `id` in `ContributionRegistry.take`.
- `plugins_read_source` takes a plugin id, never a path, and re-checks containment with canonical paths — the renderer can't name arbitrary files through it — n/a (security floor).
- A linked plugin folder (`plugins/<id>` is a symlink to a checkout) is allowed; its `plugin.js` must sit directly in the link target — supports developing a plugin in its own repo — refuse symlinked folders in `paths::contained_entry`.
- The plugin loader is a lazy chunk imported after the first React commit (`startPluginsAfterMount` in `src/main.tsx`) — first paint never waits on plugin I/O and a plugin-free start pays one small import — call `startPlugins()` inline.
- `minCodemux` is compared as three numeric dotted parts; pre-release tags are ignored — enough for a gate, no semver dependency — swap `satisfiesMinVersion` for a semver library.
- Plugin errors toast once per failed load/registration and stay on the plugin's row until the next good load — attribution without toast spam on every save — n/a.
- Windows (WebView2) was not tested for blob-module imports in milestone 1: no Windows runner or VM was available — record only; test on Windows before release.
- One pull request, updated per milestone, kept as a draft until milestone 7 — milestones build on each other and this repo's CI only runs for PRs that target main, so stacked PRs would show no checks — split by cherry-picking each milestone's commits onto its own branch.
- The `src/plugins/**` import fence is a Vitest test (`src/plugins/import-fence.test.ts`), not an ESLint rule — Codemux has no ESLint, and adding a linter for one rule is more weight than the rule; the test runs in CI with every other test — replace it with Hermes's `no-restricted-imports` block if ESLint is ever adopted.
- Bundled plugins split into `meta.ts` (eager, tiny) and `plugin.ts(x)` (lazy chunk) — the spec's "never imported when off" needs the code out of the main bundle while Settings still lists the row — merge into one eager `plugin.tsx` (Hermes's shape) and accept that off plugins ship in the main chunk.
- The kill switch still lists bundled rows (no code loaded) so Settings can show what is being held back — a blank page reads like a bug — skip `adoptBundledPlugins()` when `disabledByEnv`.
- Safe mode pauses only non-bundled plugins, matching the spec; bundled plugins follow their saved decision — they ship with the app and are reviewed with it — add `|| kind === "bundled"` to the pause check to pause everything.
- The 10-second clean-start window starts when plugin loading begins, not at process start — that is the moment a plugin could take the app down — move the timer into `main.tsx` before `mountApp()`.
- Plugin settings pages get their own "PLUGIN SETTINGS" group in the Settings nav (one entry per plugin, all of its pages stacked) — the spec mounts them in the nav, and one entry per plugin keeps the nav short — list each page as its own nav item instead in `settings-view.tsx`'s `navGroups`.
- Plugin keybind combos are normalised to the canonical order keydown produces (`Alt+Ctrl+Shift+Key`) — "Ctrl+Alt+E" otherwise never matches — drop `canonicalCombo` in `contrib/keybinds.ts` and require canonical strings.
- `transcript.toolRenderer` also replaces the opened body of a tool step inside the work log, not only the standalone `tool_call` row — most tool calls render in the work log, so the MessageList arm alone almost never fires — remove `StepBody` in `ActivityBlock.tsx`.
- Plugin themes are namespaced `plugin:<pluginId>:<id>` and validated with the custom-theme parser — they can never shadow a built-in or user theme — drop the prefix in `contrib/themes.ts`.
- `host.openRightPane` selects the pane for the active workspace and is a no-op on a chat draft (no right panel there) — switching views behind the user's back is worse than nothing — open the workspace view first in `sdk/host.ts`.
- The title-bar slot sits after the whole action island so it renders in both GUI and legacy chrome — the first placement only existed in GUI chrome — move it back inside `titlebar-utility-actions`.
- The milestone 4 backdrop test plugin is a disk plugin kept at `docs/plugins/examples/backdrop-test/plugin.js`, not a bundled one — it proves the third-party path (plain ESM, blob import, live install) that the ASCII backdrop plugin will use — move it under `src/plugins/` with a `meta.ts` to bundle it.
- The chat tap emits at the very top of `forward_event`, before any branch, so plugins see `UsageRecorded` and `PlanUsageUpdated` (swallowed for panes) and every other event exactly once — panes are unchanged because the tap is a separate `plugin_agent_event` to the main window — move the `tap::emit` call below the early returns to exclude swallowed events.
- `cache_write_ttl` is `1h` when any of the increment's cache writes were at the 1-hour tier, else `5m` when there were writes, else absent; `host.chat.onEvent` exposes it as `cacheWriteTtl` (and `subagent`) beside the raw event — mixed increments are reported by their most expensive tier — drop `cache_write_ttl()` in `claude/translate.rs`.
- A main-page reload switches the tap off (on `PageLoadEvent::Started`), since that page's listeners are gone; the new page turns it back on with its first subscriber — otherwise a reload with no plugins would leave the tap emitting forever — remove the `tap::set_enabled(false)` in `lib.rs`.
- Git installs never check out or clone a working tree: a private bare repo fetches one commit (shallow, blobless, https only, no config/credentials/hooks) and only the plugin folder's regular files are read as blobs — nothing from the repository can run and links, submodules or a repo-supplied marker are skipped — replace `install::fetch_plugin` with a clone + checkout.
- The install dialog previews one resolved commit and `plugins_install` refuses if the source now resolves to a different one — the dialog must never install something other than what it showed — drop the `expected_sha` check.
- A GitHub install follows the branch or tag in its URL for updates (`gitRef` in the marker), else the default branch; a catalog install updates to the catalog's pinned commit — "Update" then means "what this source points at now", shown before applying — store only the sha and ask for a ref on update.
- Installing never replaces a Local or linked folder, or an install from another source (a different GitHub repository or catalog entry, or Git vs catalog), with the same id; the user removes it first; a catalog entry stays the same plugin if the catalog moves it to another repository — an id alone must not transfer the user's on/off decision to another plugin — drop `install::check_replacement`.
- The fetched catalog is persisted in `plugins.sqlite` meta and refreshed 30 s after start (at most once per 24 h), so a blocklist applies at load offline — the bundled copy is only the floor — drop `catalog_now`'s seed and use the bundled catalog until a fetch.
- `CODEMUX_PLUGIN_CATALOG` (debug builds only) reads the catalog from a local file — needed to test entries and blocklists before publishing — remove the `#[cfg(debug_assertions)]` branch in `catalog.rs`.
- The install gate uses fixture branches `plugin-example-hello` / `plugin-example-hello-next` in this public repo rather than a separate repository — no new repo to own; the plugin source is `examples/plugins/hello/plugin.js` — delete the two branches.
- `docs/plugins/README.md` is the single author guide; the gate fixtures `docs/plugins/examples/{backdrop-test,usage-logger}` stay beside it as worked examples, and `examples/plugins/hello/` is the copyable starter — one doc, examples at the paths the spec names — move the fixtures under `examples/plugins/`.
- Removing add-ons deletes their CI steps that only built or tested the add-on host (Windows GNU toolchain, Secret Service credential tests, packaged runtime gate, release-policy check) and `--disable-addons` becomes an alias of `--disable-plugins` — nothing else used them, and the alias keeps old launch scripts working — restore from the add-on removal commit.
- Removing add-ons leaves an existing `addons-v1` data folder and the `addon.*` settings rows on disk untouched (per spec); no migration runs — the old system had no users — delete them by hand if wanted.
- Plugin ownership is explicit: each incarnation has one owner, `ctx.host` is bound to it, and a bare `host.*` subscription is owned only when the caller is certain (inside `register()` or a host-invoked callback). The host never guesses after an `await` — JS has no async context, and a guess hands one plugin's subscription to another — make `currentOwner()` fall back to the pending registration again.
- A toggle whose native save failed keeps governing the session and shows "Couldn't save this choice" on its row, rather than being reverted by the next rescan — a failed "off" must never turn a plugin back on — drop the failure branch in `setPluginEnabled` that keeps `unsaved`.
- Decision saves are serialized per plugin and each toggle has its own attempt number; only the latest toggle may clear its override or report an error — a failed choice belongs to the toggle it was made for — key `unsaved` by value again.
- Remove and fresh install run inside `beginInstallationChange`: it first drains every queued save for that id, keeps the plugin inactive and its switch disabled while the native step runs, keeps the old installation's choices (including a failed "off") until the step succeeds, then drops them; on failure it keeps them and rescans — no old save can land on a replacement and nothing runs in the window — drop the gate and clear overrides directly.
- `host.chat.requestCompaction` is app-owned and the plugin only chooses the moment: the session claim, the `compact-idle` sidecar RPC, hiding the compaction's output, the notice, the 10-minute give-up and Claude Code's opt-outs all live in `claude/session.rs` / `idle_compaction.rs`, and the old timer, cache tracker and `agents.idle_compaction` setting were not ported — a plugin must not be able to wedge a session or leak a hidden turn, while the policy can evolve without an app release — move the tracker back from the prototype and call `request_compaction` from a Rust timer.
- The two chat commands are named `plugins_chat_status` / `plugins_chat_request_compaction`, so the web remote's existing `plugins_*` prefix denial covers them with no new rule — plugins are desktop-only — rename them `agent_chat_*` and add them to `web_remote/policy.rs` to expose them to paired clients.
- `getStatus` returns `null` for a thread with no live session rather than a synthetic idle status; `queued` is `null` for providers with no queue of their own (only Claude and Codex keep one), and `busy` also counts delegated work holding the run open, matching `agent_chat_turn_active` — a plugin should never mistake "unknown" for "idle" — return a status with `status: "closed"` instead.
- Compaction refuses device chats and managed workflow attempts with `unsupported` — a device's CLI reads that device's Claude settings, which this computer can't check for opt-outs, and workflow attempts own their run — read the device's settings over SSH and lift the `eligible` check in `claude/session.rs`.
- The compaction notice reads "Compacted while idle" (not "…before the prompt cache expired") because the app no longer knows why the plugin chose that moment — the plugin can show its own reason — change `NOTICE_TEXT` in `idle_compaction.rs`.
- `host.reducedMotion()` is the app setting OR the OS `prefers-reduced-motion`, and `host.onReducedMotionChange` fires only when that combined value flips — a plugin should not have to combine two sources itself — return only the setting again in `sdk/host.ts`.
- A compaction that outlives its 10 minutes (or whose start RPC had an unknown outcome) is interrupted, and only a stop the sidecar confirms releases its claim and output filter (its own late `result` does not, because the interrupt can still land); if the stop isn't confirmed, the session is marked gone and its sidecar shut down with the claim still held, its queued sends are cancelled, and the next send rebuilds it from the resume cursor — releasing queued sends onto a query still running `/compact` would let its late reply and `result` land on, and end, the user's turn — release the claim on timeout without stopping the run.
- A notification belongs to the compaction that held the session when it arrived (read before the notification changes session state), and the compacting marker is sent under the same lock as the claim — a compaction claimed while the previous turn's `result` was being handled must not take that `result` as its own end — read the current claim in `settle_idle_events` again.
- Bundled plugins may import sibling files in their own folder (`./name`, no assets, no `..`), not only `@codemux/sdk` and `react` — a real plugin like the thread backdrop needs a pure, separately tested model next to its component; assets and app modules still go through the SDK — restrict `OWN_FILE` back out of `src/plugins/import-fence.test.ts`.
- The plates moved from `sidebar-empty-state.tsx` to `src/lib/plates.ts` and are exported from `@codemux/sdk` as `PLATES` / `readLastPlate` — the thread backdrop draws them and avoids the plate the sidebar is showing — move them back and inline the art in the plugin.
- `landing.backdrop` gains `onCalmChange(handler)`: the host notifies on landing resize, headline resize and any scroll inside the landing — a pull-only `calmRect()` left every backdrop to watch the app's DOM itself — drop it from `LandingBackdropProps` and the host effect.
- The thread backdrop is Official and on by default; it honours both the app's reduce-motion setting and the OS preference (drawn once, never animated) — it replaces the earlier in-core prototype, which was on with no switch — set `defaultEnabled: false` in `src/plugins/thread-backdrop/meta.ts`.
- Plugin MCP registrations are ephemeral native resources owned by an incarnation token; stable plugin/local-server ids retain Settings disable choices — executable registrations must vanish on unload and stale cleanup must not remove a replacement — persist declarations and replay only enabled plugins instead.
- Plugin tool prefixes may repeat across disjoint workspace scopes; registry tool names are ASCII and at most 50 characters (64 including Claude’s observed 14-character envelope), with a 12-hex SHA-256 suffix when changed — one integration can expose stable names in separate projects without truncation aliases — replace `plugin_tool_name` and migrate plugin guidance.
- Codex keeps initial plugin dynamic schemas plus two stable live-catalog tools, also available through the gateway — the installed 0.162.1 probe did not update dynamicTools or refresh its running-thread MCP catalog — replace the bridge with a provider refresh API after observing it work.
- The shared-token MCP gateway is unscoped and ignores URL workspace parameters — a provider must not select another workspace with a query string — add native token-bound caller identity in the gateway-identity PR.
- Plugin MCP activity excludes arguments and results and pairs start/end in a registry-owned drop guard — indicators need lifecycle signals without copying screenshots or sensitive inputs — add explicitly bounded opt-in payloads if a concrete use case needs them.

- Plugin-only MCP scope is explicit (`"plugin"`), and empty workspace lists stay invalid — UI pickers need tools before workspace consent without exposing them to agents — remove the scope variant and require a non-agent transport.
- Plugin tool descriptions use bounded per-tool replace/append edits in the registry — provider payloads must carry the same plugin guidance without repeating a global paragraph on every tool — remove `toolDescriptions` and keep server text unchanged.
- MCP unregister is awaitable and reports stopping until child exit plus call completion; immediate shutdown is opt-in and skips EOF grace — Stop indicators must be truthful and input drivers must halt promptly — restore fire-and-forget unregister and remove `shutdown`.
- Claude refresh removes and re-adds the shared SDK MCP server only between turns, coalescing changes — the observed SDK ignores replacement instances under an existing name, and active calls must retain their results — use a verified SDK in-place catalog refresh instead.
- Fixed-schema Codex threads receive one bounded, marked plugin-catalog reminder in the next input after a visible change; UI history imports strip it — the weak model must discover late plugin tools without changing collaboration mode or the user's app message — remove the input reminder after a verified provider refresh works.

- MCP listings redact environment and header values; registration tokens and page epochs remain native ownership state — another plugin or paired browser must not acquire a registration's bearer token from Settings discovery — expose credentials in list output.
- Each plugin registration carries its originating document epoch and uses a per-server lifecycle lock — delayed old-page IPC must fail and a slow Stop must not delay unrelated servers — restore command-time epoch capture and the global lifecycle lock.
- Plugin HTTP URLs require HTTPS outside loopback; MCP clients bypass proxies for loopback and do not follow redirects — app-supplied headers must stay on the intended endpoint — restore default proxy/redirect handling.
- HTTP notification streams reconnect with bounded backoff and reconcile on connection — changes while disconnected must reach live catalogs — retain a one-shot stream.
- Claude defers shared-server replacement through pending steers and queued prompts, delivering top-level results before control RPCs — a steer can become another CLI turn and refresh must not delay visible completion — swap on every result.
- Codex keeps catalog bridge tools even without active plugins; Claude adds them only when a plugin registration is visible, including one advertising zero tools — fixed Codex schemas need an entry point for future integrations, while Claude can swap native catalogs — use verified native mid-turn refresh for Codex.
- OpenCode chats see only globally scoped plugin tools in this PR; workspace scoping for OpenCode follows in the gateway-identity PR — its V2 MCP configuration is shared by directory, so a workspace URL could give another chat the wrong identity — restore per-workspace URLs.
- Claude also receives the live plugin catalog list/call tools alongside native tools — an Editor can connect during one turn, while swapping the shared SDK server must wait for a safe boundary — remove the fallback after native same-turn refresh is verified safe.

- Claude bridge calls use a PreToolUse target-permission guard and target-labelled approvals, including target-scoped permission updates — an allow on the dispatcher must never approve every present and future plugin tool — replace this with a verified CLI target-permission API.
- The Claude target guard reads effective rules through SDK 0.2.114's runtime getSettings control method, pinned by a CI protocol test, and fails closed visibly when unavailable — target deny/ask/allow rules must survive bridge dispatch without parsing settings files ourselves — use an officially exported equivalent once available.
- Claude catalog swaps have a five-second bound; timeout retains the catalog and retires the indeterminate query before the next turn resumes — a late removal response must not affect new calls and a hung control RPC must not wedge Send — use cancellable SDK control requests.
- Settings MCP listings also hide stdio arguments and URL queries/embedded credentials — CLI tokens and query tokens must not leak through informational discovery — expose a separately authorized diagnostic view if needed.
